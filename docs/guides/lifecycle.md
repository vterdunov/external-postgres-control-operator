# Database lifecycle and permissions

`Database` manages one SQL database, its declared schemas and extensions, and permissions on those objects. `DatabaseRole` manages a SQL role and its requested attributes and memberships. EPCO creates missing objects and reconciles existing objects when no competing EPCO manager is recorded. Reclaim defaults to `retain` for databases and roles. Set the corresponding reclaim policy to `delete` to request SQL cleanup when the Kubernetes resource is deleted; PostgreSQL dependency checks can still prevent deletion. An explicit `ensure: absent` requests removal while the resource exists.

Omitted permission scopes are unmanaged initially. Removing a permission previously managed by the same live Kubernetes resource revokes that managed grant; `ensure: absent` explicitly requests grant removal. Recreating a resource starts a new permission history. With retain policy, SQL grants can remain after resource deletion; use explicit absent entries to request cleanup when managing the object again.

The database owner is not automatically reassigned for existing tables. Named-table permissions require existing tables and do not create or drop them. Broad schema table and sequence permissions discover relations during reconciliation. Default privileges apply to future objects created by the declared SQL creators. Database creation properties apply when creating a database; changing them does not recreate an existing database. Extension omission retains the installed extension; explicit absence requests removal subject to PostgreSQL dependencies. `managementPolicy: observe` checks requested SQL state without changing SQL or creating application connection outputs; it requires retain reclaim policy. FDW and server fields exist in the API, but runtime management is unsupported and reports `UnsupportedFeature` with `Ready=False`.

Extension creation, update, relocation, and removal require the supplied PostgreSQL account's existing authority; EPCO does not grant extra privileges or change extension ownership to make an operation succeed. Removal uses PostgreSQL `DROP EXTENSION RESTRICT`, never `CASCADE`, so dependent application objects can block deletion.

Status distinguishes successful applied generations from observed state. Database Ready requires requested lifecycle work, permissions, exports, and required cleanup to succeed. A requested connection Secret may be created before SQL is ready, so Secret existence alone does not mean the database is usable.

# External PostgreSQL Control Operator chart

Install one manager group per Kubernetes cluster using one delivery route.
The default Deployment is `epco-controller-manager`; fixed cluster RBAC names
prevent a second Helm release or automatic adoption of a legacy installation.
Choose an explicit namespace and Kubernetes context. Namespace creation is an
external install option; the chart does not manage a Namespace or application CRs.

Chart version and application version are independent. Released image defaults
use a visible version tag and verified digest. The checked-in development tag is
not a published release. See [delivery and releases](../../docs/development.md#delivery-and-releases)
for verified OCI installation, explicit CRD upgrades, route migration and safe removal.

Helm installs CRDs from `crds/` initially but does not upgrade or remove them.
Uninstalling the chart preserves CRDs, custom resources, credentials and SQL
history. Reinstall or resume the manager to complete pending finalizers before
explicit CRD retirement.

`crds/*.yaml` and `generated/*.yaml` are generated byte-for-byte copies; never
hand-edit them. Development uses `python3 tools/chart.py sync`, then `check`.
Release assembly must provide `--inputs-dir` from the verified application
release and `--chart-dir` pointing at its temporary chart assembly.

After verifying and downloading an exact release package, install or upgrade
through the schema gate (prepare the namespace separately):

```sh
python3 tools/chart.py install --package ./external-postgres-control-operator-0.1.0.tgz \
  --release epco --namespace epco-system --context YOUR_CONTEXT
```

The gate refuses conflicting manager ownership, unreadable CRDs and unknown
retained spec fingerprints before writes. It explicitly applies supported CRDs,
waits for Established, then runs Helm with `--skip-crds`. The initial baseline
supports the identical generated spec only. Future compatible predecessors must
be explicitly reviewed and declared by the generator; version numbers alone
never authorize a schema upgrade or downgrade. Generated compatibility metadata
must travel with the verified chart package.

The manager runs as UID/GID 65532 with Restricted Pod Security settings,
including `privileged: false`. Namespace admission labels belong to your cluster
policy; this chart does not manage them.

`networkPolicy.enabled` defaults to `true` and selects only manager Pods. It
allows authenticated HTTPS metrics on TCP 8443 from same-namespace Pods when
metrics are enabled; disabling metrics leaves no peer ingress rule. Kubelet
probes retain standard node-origin access. Enforcement requires a supporting
network plugin, and other policies can add permissions. See the
[Kubernetes NetworkPolicy semantics](https://kubernetes.io/docs/concepts/services-networking/network-policies/).

For a scraper in a separate namespace, put both selectors in one peer so they
match together, for example in `monitoring-values.yaml`:

```yaml
networkPolicy:
  metricsIngressPeers:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: monitoring
      podSelector:
        matchLabels:
          app: prometheus
```

Pass `--values monitoring-values.yaml` to the schema-gated install command;
repeat `--values` for ordered overrides. The gate snapshots the package and
values, validates them before cluster writes and installs those same bytes.

Egress remains unrestricted by this chart by default, preserving external
PostgreSQL, Kubernetes API and DNS access across varying network/NAT layouts.
`networkPolicy.egress.enabled: true` requires nonempty explicit Kubernetes
`to`/`ports` allow rules in `networkPolicy.egress.rules`; configure the actual
PostgreSQL, API and DNS destinations. Empty wildcard rules and malformed values
are rejected. `networkPolicy.enabled: false` renders no policy.
